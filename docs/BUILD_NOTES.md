# おすすめビルド解説の書き方

`src/content/buildNotes.ts` に入っている、ビルド1本ごとの解説をどう作るかの手順。
ゲーム内の「推奨セット装備」を撮り直したら、この順でやり直す。

初版は 2026-08-31。116体227本を書いた。

---

## なにを書くものか

ゲーム内の人気タブは、**何を積むかは出すが理由は出さない**。
2本並んでいても、何を狙った構成なのか、どちらを選べばいいのかが分からない。
その2点だけを当サイトが書き足している。

1本につき3つ。日本語と英語の両方。

| 欄 | 中身 | 目安 |
|---|---|---|
| `label` | 何を狙った構成かの一言 | 10〜20字 |
| `when` | どういう場面で選ぶか | 15〜30字 |
| `text` | その中身。装備の効果と数値で説明する | 2〜4文 |

`when` が主役。読者が知りたいのは、まず「どっちを選ぶか」。

---

## 手順

### 1. 材料を作る

```
node scripts/build_notes_source.mjs
```

`scratch/build-notes-source/{ヒーローID}.md` が116件できる（gitignore 済み）。
中身は買う順に並べた装備6品・アルカナ・合計値・2本の違い。

**スキルの情報は入っていない。これは意図的。** 理由は次の節。

### 2. 書く

材料ファイルを読んで、下の「ルール」に従って書く。1ヒーロー1担当。
2本ある場合は、同じ担当が両方を書く（2本の関係を見る必要があるため）。

116体を人手で書くのは現実的でないので、初版は Workflow で回した。
執筆エージェントと検証エージェントを1ヒーローずつ流す2段構え。
プロンプトは下の「ルール」をそのまま渡せばよい。

### 3. 検証する

書いた本人とは別に、材料ファイルと突き合わせる担当を立てる。
初版では227本に対して181件の指摘が出て、そのすべてが数値か差の扱いの誤りだった。
**この工程を省くと数値が合わない。**

### 4. 取り込んで検査する

```
npx tsc --noEmit
npm run lint
npm run audit          # 13番がビルド解説を見る
```

監査の13番が2つを見張る。

- ビルドの本数と解説の本数が揃っているか（撮り直しで本数が変わると1本ずれる）
- 2本の `when` が同じ文字列になっていないか

さらに、スキルへの言及が残っていないかを確認する。

```
grep -o "スキル[1-4]\|奥義" src/content/buildNotes.ts   # 0件であること
```

## ルール（執筆・検証のプロンプトにそのまま使う）

### 書くのは2つだけ

読者が知りたいのは次の2つ。それ以外は書かない。

1. 何を狙った構成なのか
2. どういう場面でそれを選ぶのか

### スキルには触れない

**これはビルドの解説であって、スキルの解説ではない。**
ヒーローのスキル名、「スキル1」〜「スキル4」、「奥義」を本文に出さない。

理由は2つある。スキルの説明は同じページのスキル一覧に全文が載っているので、
繰り返す意味がない。そしてスキル仕様の読み違いが混じる原因になる。

2026-08-31 の最初の版では、材料にスキル説明も入れて「スキルと装備の噛み合いを
1つ以上必ず挙げろ」と指示した。結果はこうなった。

```
27本中15本が、装備に触れる文よりスキルだけの文のほうが多いか同数
全108文  装備に触れる45文 / スキルだけ32文
白起ビルド1 → 装備に触れる文が 0
```

検証で78件の指摘が出て、その大半がスキル仕様の読み違いだった。
材料からスキルを外して書き直した結果がこれ。

```
33本中 0本
全132文  装備に触れる92文 / スキルだけ3文
スキル名・スキル番号・奥義の出現 0件
```

装備のパッシブ説明に出てくる「通常攻撃時に」「スキル発動から5秒以内」のような語は、
その装備の発動条件なので使ってよい。禁じているのは、そのヒーロー自身のスキルの
挙動を説明することだけ。

根拠にしてよいのは次の2つだけ。

```
src/data/hok_items.json   の stats / passive / active
src/data/hok_arcanas.json の stats（1枠ぶん。装着数を掛ける）
```

数値は必ずここから足し合わせて出す。体感で書かない。

### 装備は買う順に並んでいる

`hero_item_builds.json` の `items` は買う順。2026-08-31 に確認した。

```
靴の位置        1品目 120本 / 2品目 106本 / 3品目 1本 / 4〜6品目 0本
品目別の平均価格 1,370G → 1,431G → 2,096G → 2,118G → 2,147G → 2,173G
1品目の内訳      グリードバイト54・秘法の靴31・速攻の靴25・忍びの靴22・ガーディアン救済14
```

表示順なら靴が6品目に来るビルドがあるはずだが、227本中0本だった。
だから買う順そのものが解説の材料になる。何を先に立てるかで、どの時間帯に強いかが変わる。

### 2本の差が小さいときは、無理に対立軸を作らない

ビルドが2本あるヒーロー111体の内訳（2026-08-31）。

```
装備が同じ（アルカナだけ違う）    9体   ← うち2体は買う順以外まったく同一
1品ちがい                       31体
2品ちがい                       29体
3品ちがい                       29体
4品以上                         13体
```

**40体は差が1品以下。** ここで「攻めの型」対「守りの型」のような対立を作ると嘘になる。
材料ファイルの末尾に、そのヒーローで何を書くべきかが太字で入っているので従う。

| 差 | 書くこと |
|---|---|
| 装備3品以上ちがう | 構成の性格そのものが違う。何を狙っているかの対比 |
| 装備1〜2品ちがう | その差分の装備と、買う順の違いだけ |
| アルカナだけちがう | アルカナの差と買う順 |
| 顔ぶれも同じ | **その入れ替えが何を早めるのか** |

最後の型の実例（公孫離、1品目の入れ替えだけ）。

> **ビルド1 ── 2,040Gの火力を先に立てる**
> 【レーン戦が有利で、2,040Gを早く貯められるとき】
> 最初の2,040Gをスパークダガーに回す買い方。攻撃速度+35%と、通常攻撃3回ごとの
> 電撃160〜400が靴より先に立ちます。速攻の靴は2品目に後ろ倒しで、移動速度+50が
> 入るのは2,740G地点。

> **ビルド2 ── 700Gの靴で先に足を作る**
> 【敵のガンクが早く、序盤から逃げ足を確保したいとき】
> 速攻の靴を1品目に置き、700Gの時点で移動速度+50と攻撃速度+20%を確保する。（略）
> 装備6品もアルカナ30枠もビルド1と同一で、完成後の性能差はない。

差が無いことは、正直に書く。

### when

試合前のドラフト画面や、試合中の状況を見て判断できる条件にする。

```
✓ 敵にタンクが2体以上いるとき
✓ 敵の主力ダメージが魔法に寄っているとき
✓ 序盤から前に出て、レーンを押し込みたいとき
✗ 火力が欲しいとき（読んでも選べない）
✗ 状況に応じて（何も言っていない）
```

条件の根拠は、そのビルドに入っている装備の効果か買う順に置く。
たとえば「相手の追加HPの7%」が乗る装備があれば、硬い相手ほど伸びるので
「敵にタンクが2体以上いるとき」が根拠のある条件になる。

差が大きい2本では条件を排他にする。差が1品以下なら排他にしなくてよい。
中身が同じ2本なら、条件も同じでかまわない。

### text

そのビルドが何を積み上げているかを、数値で書く。

- 合計で何がどこまで増えるか（材料の「装備＋アルカナの総合計」をそのまま使える）
- そのビルドにしかない装備の効果（割合ダメージ、復活、シールド、貫通など）
- もう1本との差（顔ぶれ・アルカナ・買う順のうち、実際に違うものだけ）

2〜4文。**各文が「この装備をなぜ、その順で積むか」に答えているか確認する。**
答えていない文は削る。

### 文体と用語

グローバルの日本語ルール（`~/.claude/CLAUDE.md` の12項目）に従う。特に効くのは4つ。

- 同じ語尾を2文続けない。「〜になります」の連続は不可
- 一文45字を目安に切る。「ただし」「つまり」「そのため」で埋めない
- 確かめたことは言い切る。「可能性があります」で逃げない
- 代名詞でぼかさない。ヒーロー名を書く

用語はサイト全体で統一済み。外すと `npm run audit` の12番が落ちる。

```
ヒーロー（チャンピオンではない）／奥義（アルティメット・ウルトではない）／
アルカナ（ルーンではない）／HP・MP（体力・マナではない）／
物理攻撃・魔法攻撃（AD・APではない）／物理防御・魔法防御（アーマー・MRではない）／
出現率（ピック率ではない）／茂み（ブッシュではない）／スロウ（スローではない）／
ガンク（ギャンクではない）／ノックアップ（打ち上げではない）／沈黙（サイレンスではない）／
ライフスティール（吸血ではない）／リコール（帰還ではない）／
サモナースペル（バトルスペルではない）／ラストヒット（CS）（トドメではない）／
ゴールド（お金・所持金ではない）／キャンプ（陣営ではない）／遠距離（遠隔ではない）／
敵ヒーロー以外のユニット（非ヒーローではない）／前衛・後衛（フロント・バックラインではない）／
ワープ（テレポートではない）

レーン名: クラッシュレーン／ジャングル／ミッドレーン／ファームレーン／ローム
（トップ・ボット・ADC は使わない）
```

英語は日本語の直訳にしない。装備名の英語は `hok_items.json` の `name_en` を引く。

## データの形

```ts
// src/content/buildNotes.ts
export const BUILD_NOTES: Record<string, { ja: BuildNote; en: BuildNote }[]> = {
  '533': [ { ja: {...}, en: {...} }, { ja: {...}, en: {...} } ],
};
```

キーは `hok_heroes.json` の `id`。配列は `hero_item_builds.json` の**ビルドと同じ並び順**。
解決は `src/lib/heroItemBuilds.ts` がサーバー側で行い、該当ヒーローのぶんだけ
`ResolvedBuild.note` に載せて渡す。116体ぶんがクライアントに乗ることはない。

表に載っていないヒーローは、解説なしでビルドだけが出る。段階的に埋められる。

## 撮り直したときに壊れること

ビルドの本数が変わると、解説が1本ずれて「ビルド2の説明がビルド1に付く」という
壊れ方をする。**見た目では気づけない。** 監査の13番がここを見張っているので、
`npm run audit` を通してから push する。

装備の中身が変わった場合は、監査では捕まらない。解説の数値が古いまま残る。
撮り直したヒーローは、材料を作り直して書き直す。
